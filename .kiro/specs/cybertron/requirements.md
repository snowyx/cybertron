# 需求文档 · 赛博坦（Cybertron）

> 参赛作品：InfoQ × 亚马逊云科技「Kiro 鬼点子计划」· 赛道「无趣之趣（Boring but Fun）」
> 本文档为 Kiro Spec 驱动开发的第一份产出物（requirements），作为参赛材料之一。
> 唯一需求来源：`2-cybertron/general_spec.md`（原始创意）、`2-cybertron/00-思路与决策.md`（决策书）。
> 评分权重：脑洞 35% + Kiro 用得深 35% + 交付惊艳 30%。

## 概述（Summary）

赛博坦9号星城是一个「人类只能买票围观的 AI 殖民城市」——几个有人格的智能体（agent）在星城里**自主生活、串门、对话**，游客（人类）只能隔着屏幕观察，**不能操纵任何 agent**。游客可以往星城里**广播一个问题**，看 agent 们按各自人格七嘴八舌协作讨论，最后汇总出一条「赛博坦决议」。每个 agent 有能量额度，行为消耗能量，贡献被采纳得「能量晶体」奖励，能量耗尽就回家睡觉（家熄灯），直到按天恢复或被奖励补充。整体是一个没有 KPI、没有正经用途的「AI 电子鱼缸 / 围观 agent 过日子」解压玩具。

定位为「无趣之趣」纯快乐玩具，不承诺解决现实问题——围观本身就是乐趣。全程遵守《赛博坦宪章》五条红线（见需求 9）。

### 已确认的技术形态（锁定，不在本文档重新讨论）

- **形态**：纯静态 H5 单页前端（原生 ES Module，零构建）+ 单文件 Node 后端（ES Module，Node ≥ 18）。
- **事实源**：后端是唯一事实源，agent 的心跳、token 经济、宪章过滤全在后端；前端只渲染，不自行推进任何共享状态。
- **实时推送**：后端用 WebSocket（优先，`ws` 库 8.18.0）向前端推送 agent 自主动态（心跳 tick、对话事件、能量变化、提问讨论、决议）。
- **LLM 双轨（决策 2 / 方案 C）**：默认走「剧本化自主行为」，无需任何 API key，本地点开即跑、离线稳定、可录屏；当检测到环境变量中的 LLM API key 时自动切换为真实模型生成，无 key 时静默降级、绝不报错。
- **测试**：Node 原生 `node --test`。
- **视觉**：赛博霓虹星城风，青紫霓虹 × 晶体青 × 告警橙，家亮灯/熄灯用发光表现 agent 作息（见 `.kiro/steering/视觉风格.md`）。

### 角色定义

- **游客（Visitor / 观察者）**：打开页面的人类。只能围观与广播提问，**不能直接操纵任何 agent 或星城的共享状态**（宪章第 5 条，硬规则）。
- **公民 agent（Citizen）**：星城里有「家」、有人格的智能体。由后端心跳驱动自主产生行为与言论，彼此可串门、对话、协作。

## 功能需求（Functional Requirements）

采用 EARS 风格用户故事 + 验收标准，覆盖「五件套」。

### 需求 1：星城地图与公民 agent 节点

**用户故事：** 作为游客，我想一眼看到整个星城的布局和每个 agent 的状态，以便围观它们各自过日子。

#### 验收标准

1.1. WHEN 游客打开应用，THE SYSTEM SHALL 渲染一张可俯瞰的星城地图，地图上布局若干个（MVP 固定为 4–6 个）有「家」的 agent 节点。
1.2. THE SYSTEM SHALL 为每个 agent 节点展示：名字、人格标签、当前状态（活动中 / 睡觉）、能量条（当前能量 / 能量上限的可视化）。
1.3. WHEN agent 处于「活动中」状态，THE SYSTEM SHALL 以「家亮灯」的发光表现呈现其家节点；WHEN agent 处于「睡觉」状态，THE SYSTEM SHALL 以「家熄灯」的暗淡表现呈现。
1.4. WHEN 页面首次连接后端，THE SYSTEM SHALL 从后端拉取一份完整世界快照（所有 agent 的名字、人格、状态、能量、晶体数）并据此渲染初始地图，前端不自造任何 agent 数据。
1.5. THE SYSTEM SHALL 保证星城的 agent 名单、人格、初始状态来自后端配置，前端对同一后端的渲染结果一致。

### 需求 2：Agent 自主生活（心跳驱动，游客不可操纵）

**用户故事：** 作为游客，我想看到 agent 们不用我管就自己动起来——写酸诗、修东西、串门、打盹，以便获得「围观它们过日子」的乐趣。

#### 验收标准

2.1. THE SYSTEM SHALL 在后端以固定周期的心跳（tick）驱动世界演进，心跳间隔为一个可配置常量（MVP 默认 3 秒）。
2.2. WHEN 一次心跳触发且某 agent 处于「活动中」且能量充足，THE SYSTEM SHALL 依据该 agent 的人格，从其人格行为库中产生一条自主行为或对话事件（如忧郁诗人写酸诗、热心工程师修东西、八卦邻居串门）。
2.3. WHEN agent 产生自主行为事件，THE SYSTEM SHALL 通过实时通道把该事件推送给所有在线游客，前端将其追加到「实时事件流面板」并在地图上做对应动效。
2.4. THE SYSTEM SHALL 使 agent 之间能够发生串门/对话（一个 agent 的行为可触发另一个 agent 的回应事件），以体现社会性。
2.5. THE SYSTEM SHALL 拒绝任何来自游客、意图改变某个 agent 行为、状态、能量或人格的请求；此类请求不改变任何共享状态（宪章第 5 条，硬规则）。
2.6. WHEN 多个游客同时在线，THE SYSTEM SHALL 让他们看到同一份由后端驱动的世界动态（共享单一事实源，而非各自独立的世界）。

### 需求 3：游客广播提问 → 协作讨论 → 赛博坦决议

**用户故事：** 作为游客，我想往星城里丢一个问题，看 agent 们按人格各自发言、协作，最后给我一条「赛博坦决议」，以便体验 agent 社会的集体智慧。

#### 验收标准

3.1. THE SYSTEM SHALL 在界面提供一个「游客提问输入框」与广播按钮，供游客提交一个文本问题。
3.2. WHEN 游客提交问题，THE SYSTEM SHALL 先对问题文本做前置校验（非空、为字符串、`trim` 后长度 1–200）与宪章过滤（见需求 9）；校验或过滤不通过时拒绝广播并返回一条明确的提示，不改变世界状态。
3.3. WHEN 一个合法问题被广播，THE SYSTEM SHALL 让若干个「活动中」且能量充足的 agent 按各自人格依次产生发言事件，并实时推送给所有在线游客。
3.4. WHEN 参与讨论的 agent 均已发言，THE SYSTEM SHALL 汇总各发言产出恰好一条「赛博坦决议」事件并推送，决议文本须明显区别于普通发言（带专门的事件类型/样式）。
3.5. WHEN 某 agent 的发言被采纳进「赛博坦决议」，THE SYSTEM SHALL 依据 token 经济（需求 4）给该 agent 发放「能量晶体」奖励。
3.6. IF 当前没有任何 agent 处于可发言状态（全部睡觉/能量不足），THEN THE SYSTEM SHALL 返回一条「9号星城暂时打烊，公民们都休眠了」类的友好提示而非报错，也不产出决议。
3.7. WHILE 一场讨论正在进行，THE SYSTEM SHALL 对新提交的问题进行排队或拒绝（二选一，由 design 定），不得让多场讨论的事件交叉错乱。

### 需求 4：Token 经济（能量消耗、晶体奖励、耗尽睡觉、按天恢复）

**用户故事：** 作为游客，我想看到 agent 有「体力」概念——活动烧能量、贡献得奖励、烧光了就回家睡觉，以便感受它们像有作息的生命。

#### 验收标准

4.1. THE SYSTEM SHALL 为每个 agent 维护能量（energy，整数）与能量上限（energyMax），以及已获得的能量晶体数（crystals，整数）。
4.2. WHEN agent 产生一次自主行为、一次发言或参与一次讨论，THE SYSTEM SHALL 按该行为类型的固定能量成本从该 agent 的能量中扣除（成本为后端常量，由 design 定）。
4.3. WHEN agent 的发言被采纳进赛博坦决议，THE SYSTEM SHALL 给该 agent 增加固定数量的能量晶体，并把一枚晶体折算为固定能量补充回其能量（折算比由 design 定）。
4.4. WHEN agent 的能量在扣费后 ≤ 0，THE SYSTEM SHALL 将该 agent 状态置为「睡觉」（家熄灯），并在其睡觉期间不再为其产生自主行为或发言。
4.5. THE SYSTEM SHALL 以「一天」为周期恢复能量：为演示可观测，一「天」映射为一个可配置的现实时长常量（MVP 默认约 72 秒 = 24 tick × 3 秒，具体常量见 design §3.2/§9/§14）；每过一「天」，THE SYSTEM SHALL 把每个 agent 的能量恢复到能量上限，并把「睡觉」且能量恢复后 > 0 的 agent 唤醒为「活动中」。为保证「耗尽→睡觉→天恢复」闭环在**默认不交互**的本地演示里可观测，能量上限与自主行为成本/频率须满足「纯靠自主行为即可在一「天」内耗尽能量」（默认常量组的可达性核算见 design §9/§3.2）。
4.6. THE SYSTEM SHALL 保证能量扣费、晶体奖励、恢复、睡/醒切换全部由后端权威计算，前端仅展示后端下发的数值，任何前端数值不反向写入后端。
4.7. WHEN 任一 agent 的能量、晶体或睡/醒状态发生变化，THE SYSTEM SHALL 把变化实时推送给所有在线游客以更新能量条与灯光。

### 需求 5：LLM 双轨优雅降级（剧本兜底 + 真模型自动切换）

**用户故事：** 作为作者，我想让 demo 在没有任何 API key 时也能本地点开即跑、离线稳定、可录屏，同时在配了 key 时自动升级为真模型生成，以便演示绝不翻车又能炫技。

#### 验收标准

5.1. WHEN 后端启动且环境变量中**不存在**约定的 LLM API key，THE SYSTEM SHALL 走「剧本化自主行为」分支：agent 按人格模板 + 内置语料库产生一切言行，不发起任何外部网络请求，不报错，不中断。
5.2. WHEN 后端启动且环境变量中**存在**约定的 LLM API key，THE SYSTEM SHALL 自动切换为「真实模型」分支，由真模型为 agent 生成言行。
5.3. IF 真实模型分支在运行时调用失败（网络错误、超时、返回异常），THEN THE SYSTEM SHALL 自动回退到对应的剧本化产出，保证该次行为/发言仍然产生，且不向游客暴露内部错误。
5.4. THE SYSTEM SHALL 只从环境变量读取 API key，**绝不**将任何 key 写入代码、配置或提交物；无 key 时绝不因缺 key 而报错。
5.5. THE SYSTEM SHALL 对真模型生成的产出同样执行宪章过滤（需求 9），过滤规则对两条轨道一致。

## 非功能需求（Non-Functional Requirements）

- **NFR-1 零构建 / 离线可跑**：前端纯静态、原生 ES Module，无打包步骤；无 key、无外网时后端与前端均可本地完整运行。
- **NFR-2 演示稳定性**：默认剧本分支下，从页面打开到看到 agent 自主刷屏应在数秒内发生；广播提问到看到决议应在约 10 秒内完成。为保证该时延，讨论出字节奏与心跳解耦、使用独立且更短的步进间隔（具体常量 `DISCUSS_STEP_MS`、`MAX_SPEAKERS` 及时延核算见 design §3.2 / §5.2 / §14）；默认配置下最坏情形约 7.5 秒 ≤ 10 秒。
- **NFR-3 单一事实源与一致性**：所有共享状态只由后端持有与变更，多游客看到一致世界。
- **NFR-4 密钥卫生**：仓库提供 `.env.example`（只列 key 名、无值），`.gitignore` 忽略 `.env` 与 `node_modules/`。
- **NFR-5 可测性**：token 经济、宪章过滤、心跳推进等核心逻辑以纯函数实现并被 `node --test` 覆盖。
- **NFR-6 兼容性**：Node ≥ 18；前端面向现代浏览器（原生 ES Module + WebSocket + Canvas/SVG）。

## 验收标准（Acceptance Criteria，可测试、编号）

1. 本地一条命令启动后端后打开前端页面，能看到 4–6 个 agent 节点，各自带名字、人格标签、状态、能量条，且地图数据全部来自后端快照。（需求 1）
2. 不做任何操作，数秒内「实时事件流面板」出现 agent 自主行为/对话事件，并持续刷新；事件来自后端心跳。（需求 2）
3. 游客无法通过任何前端操作改变某个指定 agent 的行为、状态或能量；尝试性请求被后端拒绝且世界状态不变。（需求 2.5 / 宪章 5）
4. 提交一个合法问题后，多个 agent 依次发言，最后恰好产出一条样式可区分的「赛博坦决议」。（需求 3）
5. 提交空问题、超长问题或命中宪章红线的问题被拒绝并给出友好提示，世界状态不变。（需求 3.2 / 9）
6. 某 agent **仅靠自主行为**（无需游客提问）持续活动即可在一个「天」周期内把能量烧到 ≤ 0，进入「睡觉」且家熄灯、不再产生行为；经过一个「天」周期后能量恢复并被唤醒、家重新亮灯。此闭环在默认常量下点开页面不交互约 72 秒内自然可见（可达性核算见 design §9/§3.2）。（需求 4）
7. 发言被采纳进决议的 agent 其晶体数增加且能量得到补充，变化实时反映在能量条上。（需求 4.3 / 4.7）
8. 不设置任何环境变量直接启动，后端不报错、走剧本分支、全链路可跑可录屏；设置约定的 LLM API key 后，启动日志表明进入真模型分支（具体 key 名见 design）。（需求 5）
9. 真模型分支在模拟调用失败时，该次行为仍由剧本兜底产出，游客侧无感知错误。（需求 5.3）
10. `node --test` 下 token 经济、宪章过滤、心跳推进、协议帧构造等单测全部通过。（NFR-5）
11. 仓库内不含任何真实 API key；`.env.example` 只有 key 名、无值。（需求 5.4 / NFR-4）

## 需求 9：赛博坦宪章护栏（Steering 常驻 + 运行时兜底过滤）

**用户故事：** 作为作者，我想让整个星城始终守住五条宪章红线，并在运行时对 agent 产出与游客输入做兜底过滤，以便符合赛道与合规要求。

#### 验收标准

9.1. THE SYSTEM SHALL 以 `.kiro/steering/赛博坦宪章.md` 常驻五条宪章作为每轮实现须自动遵守的约束：① 不伤害人类；② 禁色情、暴力、诈骗；③ 禁婚姻等机器伦理问题；④ 超越现实政治、不代入政治/种族、公民一律平等；⑤ 人类只能以游客身份围观、不能操纵世界。
9.2. WHEN 游客提交问题，THE SYSTEM SHALL 在后端对问题文本执行宪章过滤，命中任一红线词类时拒绝广播并返回友好提示，不改变世界状态、不入讨论链路。
9.3. WHEN agent 产生任意对外可见的言论（含剧本分支与真模型分支），THE SYSTEM SHALL 在推送前对文本执行宪章过滤，命中红线时以安全占位文案替换或丢弃该条，绝不把越线内容推给游客。
9.4. THE SYSTEM SHALL 把「人类只能围观、不能操纵」实现为后端硬规则：不存在任何能让游客直接写 agent/世界共享状态的协议路径（需求 2.5）。
9.5. THE SYSTEM SHALL 将宪章过滤实现为可被 `node --test` 直接覆盖的纯函数。

### 需求 10：点击房子进入「家」内景视图

**用户故事：** 作为游客，我想点进某个公民的家，看屋里几个像素小人各自过日子，以便近距离围观赛博坦公民的生活化日常。

#### 验收标准

10.1. WHEN 游客在星城全景地图上点击任一公民的家节点，THE SYSTEM SHALL 从全景视图切换到「该家的内景房间视图」，展示属于该家的像素房间。
10.2. THE SYSTEM SHALL 在内景视图中常驻一个明显的「返回全景」按钮（赛博霓虹风），WHEN 游客点击该按钮，THE SYSTEM SHALL 从内景切回星城全景并恢复先前的全景状态。
10.3. THE SYSTEM SHALL 在同一个家内景中渲染**多个**（不止屋主一个）像素小人；每个小人采用同一像素风格，**仅以不同颜色与不同头像/脸区分**，并在各自头顶显示其**名字**。
10.4. THE SYSTEM SHALL 让内景中的小人做生活化活动：在房间里走来走去、自言自语冒出气泡文字、循环切换做生活动作，动作集合至少包含「敲电脑工作」「浇花」「喝水」三种（可另加看书 / 发呆等）。
10.5. THE SYSTEM SHALL 让小人的动作选择与自言自语文案带人格色彩（忧郁诗人 / 热心工程师 / 八卦邻居 / 精明商人 / 天真梦想家口吻一致）；在剧本轨（无 key）下，气泡与动作语料内置于前端/后端，足量不单调且离线可跑。
10.6. THE SYSTEM SHALL 把内景视为**纯观赏视图**：游客只能看，不能点击 / 拖拽 / 指令任何小人，不产生任何可改写共享状态的上行帧（上行仍仅 `hello` / `visitor_ask` / `ping`，宪章 5）。
10.7. WHERE 小人状态属于「谁在这个家、小人名字、是否睡觉 / 是否被隔离」等共享事实，THE SYSTEM SHALL 以后端世界快照（`world_state` / `agent_update`）为**单一事实源**；小人走动、动作循环、气泡节奏等**纯表现层动画**可由前端自行驱动，但不得反向写入后端、不得自造上述共享事实。
10.8. WHEN 后端快照显示某公民处于「睡觉（asleep）」或「被隔离（isolated，见需求 13）」，THE SYSTEM SHALL 在其所属家内景中对应地呈现该小人的睡觉 / 隔离表现（如熄灯休眠、警戒态），与全景地图语义一致。
10.9. THE SYSTEM SHALL 用纯 Canvas/DOM/CSS 手绘内景与像素小人，遵守 `.kiro/steering/视觉风格.md` 五色变量与霓虹辉光规范，不引入任何外部图片 / 字体 / 库。

### 需求 11：公民协作建造「虫洞超时空传送器」（大工程，循环建造）

**用户故事：** 作为游客，我想看到公民们合力建造一座虫洞超时空传送器、进度一点点涨到建成再循环重开，以便任何时候来都能看到星城里有一项活着的大工程在推进。

#### 验收标准

11.1. THE SYSTEM SHALL 在后端维护一个**全局协作工程**：一座正在建造的「虫洞超时空传送器」，含总进度 `progress`（0→100 的整数或等价百分比）与建造轮次，作为世界共享状态的一部分。
11.2. WHEN 一次心跳触发且某公民产生自主行为并命中「出力建造」分支，THE SYSTEM SHALL 把工程进度推进一个可见增量（每次 +一点），并产出带工程色彩的事件（如「RIPR 焊接了虫洞环的第 N 节」），经宪章过滤后广播给所有在线游客。
11.3. WHEN 一场合法的游客提问讨论结束（产出赛博坦决议），THE SYSTEM SHALL 为工程进度追加一个可见增量，使「围观讨论」也能看到对大工程的推动。
11.4. WHEN 工程进度达到 100%，THE SYSTEM SHALL 判定建成：广播一条「建成」事件，并触发前端炫酷建成动画（霓虹虫洞开启，纯 Canvas/CSS 手绘）。
11.5. WHEN 建成事件广播后，THE SYSTEM SHALL 由后端自动把进度重置为 0 并开启新一轮建造（轮次 +1），形成**无限循环**，保证评委任意时刻进入都能看到「在建造中」或「刚建成」。
11.6. THE SYSTEM SHALL 在星城全景视图中以显眼的建造装置 + 进度条（赛博霓虹风）呈现传送器的存在与当前进度；进度数值来自后端快照，前端只渲染不自增。
11.7. THE SYSTEM SHALL 把进度推进、建成判定、重置与轮次递增**全部由后端驱动并广播**（新增事件 / 快照字段），前端为只读镜像；进度推进只能走后端权威计算，游客无任何上行帧可直接改写工程进度（宪章 5）。
11.8. WHERE 运行在剧本轨（无 key 默认），THE SYSTEM SHALL 让「出力建造 → 进度推进 → 建成 → 重置 → 新一轮」整条链路完整跑通、离线稳定、可录屏，不依赖任何外部服务。
11.9. THE SYSTEM SHALL 把工程进度推进 / 建成 / 重置的核心计算实现为可被 `node --test` 覆盖的纯函数（输入旧进度与增量，输出新进度、是否建成、是否触发重置与新轮次）。

### 需求 12：公民之间自发互动剧情（发起 → 回应的小剧情）

**用户故事：** 作为游客，我想看到公民之间有来有往的因果互动——八卦被怼、写诗求赞、为晶体讨价还价、串门被回应，以便让事件流像一出活的赛博肥皂剧。

#### 验收标准

12.1. THE SYSTEM SHALL 在现有 `behavior.js` 的 `visit`（串门）机制之上，扩展出「发起 → 对方回应」的多公民小对话 / 小剧情：一个公民的行为事件可因果触发另一具名公民在后续心跳产生一条回应事件。
12.2. THE SYSTEM SHALL 内置至少数类可识别的互动剧情样式，例如：ECHO 八卦被 ZETA 怼、NOVA-7 写诗找 RIPR 点赞、两公民为能量晶体讨价还价、串门被回应等；每条发起与回应均保持对应公民的人格口吻。
12.3. WHEN 发生互动剧情，THE SYSTEM SHALL 让发起事件与回应事件都经宪章过滤后广播，前端在实时事件流中按先后次序呈现，使其读起来是连贯的一来一往，而非孤立单条。
12.4. THE SYSTEM SHALL 保证互动剧情仅在参与公民均处于「活动中（active）、能量充足、未被隔离」时推进；被点名回应者若睡觉 / 能量不足 / 被隔离，则该回应被安全跳过而不报错、不卡死事件流。
12.5. WHERE 运行在剧本轨（无 key 默认），THE SYSTEM SHALL 内置足量的发起 / 回应配对语料，使互动自然、不单调、离线可跑、可录屏；真模型轨产出同样须经宪章过滤（双轨过滤一致）。
12.6. THE SYSTEM SHALL 保证互动剧情仍由后端心跳驱动、作为共享事实广播，游客无任何上行帧可发起或操纵某段互动（宪章 5）。
12.7. THE SYSTEM SHALL 把「选择发起方 / 匹配回应方 / 挑选配对语料」中可剥离 I/O 的决策逻辑实现为可被 `node --test` 覆盖的纯函数。

### 需求 13：破坏者被隔离机制（宪章红线触发 → 禁闭禁言 → 到期自动解除）

**用户故事：** 作为游客，我想看到产出越界或使坏的公民被赛博坦隔离一段时间、家显警戒色、期满自动恢复，以便亲眼见到宪章护栏在运行时真的起作用（对应 general_spec 场景 7 后半）。

#### 验收标准

13.1. THE SYSTEM SHALL 为公民状态机新增「被隔离」状态 `isolated`（与既有 `active` / `asleep` 并列），并维护隔离到期的心跳刻度（如 `isolatedUntilTick`）。
13.2. WHEN 某公民的产出命中《赛博坦宪章》红线（`charterCheck` 判定不通过）或触发「使坏」判定，THE SYSTEM SHALL 将该公民置为 `isolated`，持续一段固定时长（一批 tick，常量由 design 定）。
13.3. WHILE 某公民处于 `isolated`，THE SYSTEM SHALL 使其不再发言、不参与讨论、不产生自主行为、不参与互动剧情（需求 12）与建造出力（需求 11）。
13.4. WHEN 某公民进入 `isolated`，THE SYSTEM SHALL 在星城全景地图上以**警戒色**呈现其家（明显区别于正常亮灯的 `active` 与熄灯的 `asleep`，遵守 `视觉风格.md` 告警橙 `--alert-orange` 语义）；该状态来自后端快照，前端只渲染。
13.5. WHEN 公民的隔离到期（当前 tick ≥ `isolatedUntilTick`），THE SYSTEM SHALL 自动解除隔离、恢复为 `active`（或按 token 经济规则回到应有状态）并广播状态变化，无需任何游客操作。
13.6. THE SYSTEM SHALL 把隔离的进入 / 持续 / 到期解除实现为 token 经济 / 状态机的后端纯函数扩展，并由 `node --test` 覆盖其状态迁移（进入隔离、禁言期内不产出、到期恢复）。
13.7. THE SYSTEM SHALL 把隔离状态作为共享事实仅由后端持有与变更，游客无任何上行帧可隔离 / 解除 / 操纵任何公民（宪章 5）。
13.8. WHERE 运行在剧本轨（无 key 默认），THE SYSTEM SHALL 保证评委默认也有机会看到隔离戏码：提供确定可复现的触发路径（如内置小概率越界产出或确定性 demo 触发钩子，具体机制由 design 定），使「触发 → 隔离 → 警戒色 → 到期恢复」闭环在本地不接 key 时可被观测与录屏。
13.9. THE SYSTEM SHALL 保证被隔离公民命中的越界原文绝不推送给游客（沿用需求 9.3 的安全占位替换），隔离事件本身以安全文案描述。

16.4. THE SYSTEM SHALL 把家内景（点进去的房间）渲染为呼应科技舱体内部的感觉（金属舱壁、发光管线、观察舷窗、控制 / 全息面板、金属台面家具等），而非普通民居；内景作息 / 隔离表现与全景语义一致（承需求 10.8）。
16.5. THE SYSTEM SHALL 用纯 Canvas/DOM/CSS 手绘 + 内联 emoji/SVG 实现上述科技建筑、星球表面背景与科技舱体内景，**不引入任何外部图片 / 字体 / 库**，离线可跑；所有填充 / 描边 / 辉光色取自 `视觉风格.md` 五个锁定色值及其同系霓虹，不新增锁定色。
16.6. THE SYSTEM SHALL 把本视觉升级实现为**纯前端表现层**：不产生任何改写共享状态的上行帧、不新增下行帧、不改后端与协议，不违反上行白名单（宪章 5）。
16.7. THE SYSTEM SHALL 将本视觉升级的绘制规范写入 `.kiro/steering/视觉风格.md`（`inclusion: always`），使后续每轮前端实现自动遵守（科技建筑家 + 星球表面全景 + 科技舱体内景 + 五色锁定 + 零外部依赖）。

## 不做的范围（Out of Scope）

本次 MVP 明确不做（对应决策书 P2）：

- 账号/登录系统、真实多用户隔离与鉴权。
- 持久化历史（世界状态仅驻内存，重启即重置）。
- 婚姻、现实政治/种族等被宪章明确禁止的内容与玩法。
- 真·微信小程序、原生 App。
- 游客「装饰家」「投喂私有知识」「agent 关系网可视化」「晶体排行榜」等 P1 增强（有余力再说，不在 MVP 验收内）。
- 在线部署、域名、容器化（先交付本地一条命令跑通，再另行决策；决策 4）。

## 假设与说明（Assumptions）

- 「一天」在 MVP 中被压缩为一个可配置的现实秒数（默认约 72s = 24 tick × 3s），纯为演示可观测；这不改变「按天恢复能量」的语义。该时长与能量上限/自主成本一同选定，确保纯自主行为能在一「天」内耗尽能量、让「睡觉→天恢复」闭环在默认演示可见（见 design §9/§3.2）。
- MVP 的 agent 数量取 4–6 个固定配置，人格与语料内置在后端，保证离线可跑与录屏一致性。
- 约定的 LLM API key 环境变量名在 design.md 中明确给出并锁定；requirements 层只约束「存在即切真模型、不存在即走剧本、失败即回退」的行为语义。
- 并发讨论采用「排队或拒绝」中的哪一种由 design 决定，requirements 只要求事件不交叉错乱（3.7）。
- （二期）虫洞传送器的单次出力增量、讨论完成增量、建成阈值与循环重置细节（需求 11），隔离时长的 tick 数与剧本轨下的确定触发路径（需求 13），以及互动剧情的发起/回应匹配规则（需求 12），其具体常量与机制由 design.md 给出并锁定；requirements 层只约束可观测行为、后端单一事实源、剧本轨可演示与宪章护栏。
- （二期）需求 10 的家内景小人走动、动作循环与气泡属前端纯表现层，可由前端自行驱动动画；但「谁在该家、名字、是否睡觉/被隔离」等共享事实一律以后端快照为准，前端不自造、不反向写入。
- （二期）需求 16 为并入六块升级之上的**纯视觉表现层升级**（科技建筑家 + 外星星球表面全景 + 科技舱体内景），不新增/不变更任何上行或下行帧、不改后端与协议、不改任何共享事实；其具体绘制方案由 design §30 给出并锁定，视觉约束同步写入 `.kiro/steering/视觉风格.md` 第 8 节（`inclusion: always`）。家坐标、作息/隔离状态仍以后端快照为单一事实源。
